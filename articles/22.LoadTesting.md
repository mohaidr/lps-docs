# Load Testing

A **load test** (often called an *average-load* or *expected-peak test*) validates how your API performs under the **normal and anticipated peak traffic** it handles in production. It follows a clean, reproducible three-part shape: **gradual warm-up ramp → steady plateau → natural drain**.

Run load tests after a [Smoke Test](21.SmokeTesting.md) passes and before pushing into [Stress](23.StressTesting.md), [Spike](24.SpikeTesting.md), [Breakpoint](25.BreakpointTesting.md), or [Soak](26.SoakTesting.md) tests.

---

## What a Load Test Answers

- **SLA compliance:** Does the service meet its response-time (`P95` / `P99`) and error-rate targets at expected concurrency and throughput?
- **Warm-up behavior:** Do connection pools, caches, and JIT compilation settle smoothly during ramp-up?
- **Baseline comparison:** Did a new code release or infrastructure change regress latency or throughput compared to the previous release under the exact same workload?

---

## Runnable YAML Load Test Plan

**Example assumptions:** expected peak production concurrency is 100 clients, clients ramp up smoothly over ~1 minute (`arrivalDelay: 600` ms) to avoid cold-cache shock, and each client runs for 30 minutes (`duration: 1800` seconds). Strict `failureRules` grade SLA compliance at the end of the run, while looser `terminationRules` act as a safety stop if the test environment is severely unhealthy.

```yaml
name: ExpectedLoadTest
variables:
- name: targetUrl
  value: https://api.example.com/resource
rounds:
- name: ExpectedLoadRound
  numberOfClients: 100
  arrivalDelay: 600
  iterations:
  - name: GetResource
    mode: D
    duration: 1800
    httpRequest:
      url: $targetUrl
      httpMethod: GET
    failureRules:
    - metric: "ErrorRate > 0.01"
      errorStatusCodes: ">= 500"
    - metric: "TotalTime.P95 > 500"
    terminationRules:
    - metric: "ErrorRate > 0.15"
      errorStatusCodes: ">= 500"
      gracePeriod: "00:01:00"
    - metric: "TotalTime.P95 > 3000"
      gracePeriod: "00:01:00"
```

Run the plan with:

```bash
lps run ExpectedLoadTest.yaml
```

---

## How This Traffic Behaves

- **Warm-up (`0:00–1:00`):** 100 clients arrive one by one every 600 ms (~59.4 seconds total), giving caches, database pools, and worker threads time to warm up naturally.
- **Steady plateau (`1:00–30:00`):** Because `duration: 1800` is measured per client from its own start time, all 100 clients overlap and maintain a steady 100-client plateau for ~29 minutes.
- **Natural ramp-down (`30:00–31:00`):** Clients finish in the same staggered 600 ms cadence they started.

---

## Choosing `D` Mode vs. Paced `DCB` Mode

| Mode | Behavior per client | Best when |
| --- | --- | --- |
| `mode: D` | Sends the next request immediately after the previous response finishes | Benchmarking service-to-service APIs or maximum per-client throughput |
| `mode: DCB` | Sends `batchSize` requests, pauses `coolDownTime` ms, and repeats for `duration` | Simulating human users or callers with realistic think time between actions |

Example `DCB` iteration snippet for paced users (1 request, 1-second pause):

```yaml
  - name: PacedUserBrowse
    mode: DCB
    duration: 1800
    batchSize: 1
    coolDownTime: 1000
```

---

## Best Practices

- **Size load from real production evidence:** Derive concurrency, request rate, and read/write mix from production telemetry—label any invented numbers clearly as assumptions.
- **Pair `failureRules` with safety `terminationRules`:** `failureRules` grade the completed run against tight SLAs (e.g. `< 1%` errors, `P95 < 500` ms) without interrupting traffic, while looser `terminationRules` avoid hammering a broken staging environment for 30 minutes.
- **Test in production-like staging:** Undersized dev/QA environments produce misleading latency numbers; only run load tests against systems you own or have explicit authorization to test.
