# Soak Testing (Endurance Testing)

A **soak test** (also called an *endurance* or *stamina* test) runs **typical or sustained production traffic over an extended period**—usually **4 to 24+ hours**—to uncover slow-moving reliability problems that short 15-minute load tests never reach.

Run soak tests after your [Load Test](22.LoadTesting.md) confirms the system is healthy over a normal 30-minute window.

---

## What a Soak Test Uncovers

- **Memory leaks & GC pressure:** Gradual heap growth that triggers heavy garbage-collection pauses or `OutOfMemory` crashes after several hours.
- **Connection & handle leaks:** Unclosed database connections, HTTP sockets, file descriptors, or thread-pool starvation.
- **Storage & log exhaustion:** Disk space filling from verbose logs, temp files, uncompacted tables, or growing message queues.
- **Token, cache, or certificate expiry:** Background credential rotations, TTL evictions, or connection-pool stale DNS issues that only occur across hour boundaries.

---

## Why Paced `DCB` Mode Matters for Soak Tests

Running `mode: D` with zero delay between requests for eight hours fires tens of millions of back-to-back calls—turning an endurance test into an unrealistic 8-hour stress hammer. Using **`mode: DCB`** (`batchSize` + `coolDownTime`) paces each virtual client steadily so request volume matches realistic sustained production traffic over many hours.

---

## Runnable YAML Soak Test Plan

**Example assumptions:** sustained traffic is 50 clients ramping smoothly over ~30 seconds (`arrivalDelay: 600` ms), each client sends 1 request followed by a 1-second pause (`batchSize: 1`, `coolDownTime: 1000` ms) for **8 hours** (`duration: 28800` seconds), severe sustained degradation terminates the run, and tight `failureRules` grade final SLA compliance.

```yaml
name: EightHourSoakTest
variables:
- name: targetUrl
  value: https://api.example.com/resource
rounds:
- name: SoakRound
  numberOfClients: 50
  arrivalDelay: 600
  iterations:
  - name: SoakResource
    mode: DCB
    duration: 28800
    batchSize: 1
    coolDownTime: 1000
    httpRequest:
      url: $targetUrl
      httpMethod: GET
    failureRules:
    - metric: "ErrorRate > 0.01"
      errorStatusCodes: ">= 500"
    - metric: "TotalTime.P95 > 1000"
    terminationRules:
    - metric: "ErrorRate > 0.10"
      errorStatusCodes: ">= 500"
      gracePeriod: "00:05:00"
    - metric: "TotalTime.P95 > 5000"
      gracePeriod: "00:05:00"
```

Run the plan with:

```bash
lps run EightHourSoakTest.yaml
```

## Critical Multi-Hour Considerations

1. **Watch windowed metrics, not just cumulative `ErrorRate`:**
   - `ErrorRate` in rules is cumulative across the iteration. After 7 clean hours, even a 100% outage in Hour 8 is diluted by the millions of earlier successful requests and can take many minutes to cross `ErrorRate > 0.10`.    Always inspect **windowed** latency and error trends over time in the live dashboard or [Grafana Integration](../grafana-integration.md).
2. **Refresh pooled HTTP connections (`lps httpclient`):**
   - Over multi-hour runs, load balancers and backend IPs can rotate. Configure a pooled connection lifetime (for example `lps httpclient --poolconnectionlifetime 300`) so sockets periodically refresh DNS and avoid pinning to stale nodes.
3. **Protect the load generator (`lps watchdog` & `lps logger`):**
      - Enable [WatchDog](6.WatchDog.md) limits on the generator machine and keep console/file logging at `Warning` or `Error` (`lps logger`) so local log files do not fill the generator's disk during an overnight run.
4. **Correlate with backend infrastructure metrics:**
   - LPS measures client-visible latency, throughput, and errors—pair those timelines with server RAM, GC pauses, DB pool usage, and disk I/O to spot linear resource creep before it causes failures.
