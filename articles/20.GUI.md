# LPS GUI: Create, Run, and Review Tests in the Workspace

The LPS Workspace is a local browser interface for preparing HTTP tests, checking requests, configuring workloads, and reviewing test runs. It uses the LPS engine: the GUI changes how you work with a test, not what a client, round, iteration, or rule means.

The Workspace has three pages: **Editor**, **History**, and **Settings**. During a run, **Monitoring** opens the live metrics dashboard.

> **Generally available:** The Workspace GUI is GA starting with **LPS 3.0.6.9**. Install version **3.0.6.9** or a later stable release to use `lps ui`. Use `lps ui --help` to check the available options. For installation instructions, see the [LPS introduction](../readme.md).

> Run tests only against systems you own or are authorized to test. Start with a small workload. **Test API** also sends a real HTTP request, so a request that creates, updates, or deletes data can have real side effects.

## Start the GUI

With the .NET SDK installed, install LPS 3.0.6.9:

```bash
dotnet tool install --global lps --version 3.0.6.9
```

If LPS is already installed, update it instead:

```bash
dotnet tool update --global lps --version 3.0.6.9
```

Then start the GUI:

```bash
lps ui
```

LPS starts a local Workspace host and opens:

```text
http://127.0.0.1:8010/workspace
```

The host runs in the background by default. Running `lps ui` again reuses a compatible host already running on that port. Closing the browser tab does not stop the host or an active test.

### Startup Options

| Option | Purpose |
| --- | --- |
| `--port 8011` | Use a different Workspace port. Valid ports are 1024 through 65535; the default is 8010. |
| `--open-browser false` | Start or reuse the host without opening a browser. |
| `--data-directory <path>` | Choose the directory used for saved Workspace data. |
| `--foreground true` | Run the host in the current terminal instead of the background. |
| `--webroot <path>` | Use a custom directory containing the built frontend assets. Normally unnecessary for an installed build. |

For example:

```bash
lps ui --port 8011 --open-browser false
```

Open `http://127.0.0.1:8011/workspace` manually. The Workspace binds to the local loopback interface; it is not a remotely accessible team server.

The default data directory is `LPS/Workspace` under the operating system's local application-data directory. On Windows, this is normally `%LOCALAPPDATA%\LPS\Workspace`. To use a separate directory:

```bash
lps ui --port 8011 --data-directory ./lps-workspace
```

If an existing host on that port uses a different explicitly requested data directory, LPS reports the mismatch. Choose another port or stop the existing host first.

### Stop the Host

```bash
lps ui stop
```

For a custom port:

```bash
lps ui stop --port 8011
```

Host shutdown waits for an active test to finalize. This is different from closing a tab, and different from stopping only the current test in the Editor.

## Find Your Way Around

| Area | What It Is For |
| --- | --- |
| **Tests** explorer | Find saved tests, expand their structure, and select a round or iteration. |
| **Editor** | Edit the selected test, check its HTTP request, set its workload and rules, and start a run. |
| **History** | Select a previous run and inspect its retained results and output. |
| **Settings** | Configure the engine settings exposed by the GUI. |
| **Monitoring** | Open the live metrics dashboard for an active run. |

The **Local engine** indicator shows that the browser can communicate with the Workspace host. It does not indicate whether the target API is healthy or whether a test is running.

## Create a First Test

1. Choose **New test** in the Tests explorer and give the test a descriptive name.
2. Select its round and iteration. A round groups work; an iteration defines an HTTP operation and its execution settings.
3. Set the request method, URL, and HTTP version. Add any required headers and body in **Request**.
4. Use **Test API** to check the selected request before increasing the workload.
5. In **Workload**, start with a small number of users and a bounded request count or duration.
6. Review **Failure rules**, **Termination rules**, and **Skip conditions** as needed.
7. Choose **Save**, or choose **Run test** to validate, save, and launch the current plan.

For a small starting point, use five users, a 1,000 ms arrival delay, and one request-count iteration with ten requests per user. That describes 50 planned requests, before effects such as retries, skips, or early termination. Use a non-destructive endpoint for the first run.

For the underlying execution model, see [Rounds](../concepts/1.Rounds.md), [Iterations](../concepts/2.Iterations.md), and [Iteration Modes](../concepts/3.Iteration_Modes.md).

## Import a HAR Capture

Instead of building a test by hand, you can import a HAR file exported from a browser's developer tools and turn its captured traffic directly into an editable draft test.

1. In Chrome or Edge, open DevTools' **Network** tab, browse the target application, then right-click the request list and choose **Save all as HAR**.
2. In the Tests explorer, choose **Import HAR** and select the exported file.
3. Review the host checklist (the dialog tallies hosts from the file so you can exclude third-party domains such as analytics or CDNs), then set a test name, round name, and starting workload.
4. Choose **Import** to convert the capture into a plan, using the same filtering and conversion logic as [`lps record`](18.Record.md): noisy resource types (images, stylesheets, fonts) and infrastructure requests are dropped by default, hop-by-hop headers are not replayed, and multipart file fields become placeholder paths you must point at a real file.
5. Review the captured request count, any warnings, and any file upload placeholders, then choose **Open in editor** to load the result as a new, unsaved draft. Nothing is written to the workspace until you choose **Save**.

A HAR capture never includes the bytes of an uploaded file, and it imports cookies, authorization headers, and tokens exactly as captured. Review the **Request** tab — especially headers and any replayed session tokens — before sharing, committing, or running the imported test against anything but your own target.

## Build the Request

The request line contains the HTTP method, request URL, and HTTP version. The visual editor offers HTTP 1.1 and HTTP 2.0.

The **Request** tab contains the header table and body editor. The body editor preserves raw text and supports JSON or text editing. In the current GUI, body editing is disabled for GET, HEAD, DELETE, and OPTIONS without discarding the existing payload.

### Test API Versus Run Test

These actions serve different purposes:

| Action | Behavior |
| --- | --- |
| **Test API** | Sends the selected draft HTTP request once through the local Workspace host. It does not save the plan or start a load run. |
| **Save** | Persists the current test configuration without running it. |
| **Run test** | Validates and saves the current plan, then starts an engine run from that saved plan. |

Use the request response preview to inspect the result of **Test API**. Cancelling the request does not discard the draft. A successful single request confirms basic connectivity and request construction; it does not establish performance under concurrent load.

## Configure Rounds, Iterations, and Workloads

Use the round and iteration controls to select, add, duplicate, reorder, or remove work. Each iteration retains its own request and execution settings. Switching configuration tabs does not save or discard the draft.

The **Workload** tab describes how users arrive and how long their work lasts. Keep these quantities separate:

- **Users** are simulated clients, not a count of HTTP requests.
- **Arrival delay** spaces client launches. A zero delay represents a burst of launches.
- **Request count** determines work performed by an iteration in request-count mode.
- **Duration** bounds work in duration mode.
- **Stages** divide user launches into successive portions of a round's workload.

An arrival delay is not the delay between every HTTP request. Likewise, launching the last user does not mean the test has finished: users already launched may still be working.

### Staged Workloads

Stages let you change the number of new users and their arrival spacing over the course of a round. A stage can also have a startup pause. For example, launch a small group first, add a larger group, and then increase the launch rate for the final stage.

The stage launch windows are shown beneath the chart and beside the stage names in its table. Pauses and the period after the last launch are not additional stages.

## Read the Estimated Active-User Chart

The chart in **Workload** is a planning estimate, not a measurement from a running test. It estimates **total active users** over time using the current round settings and an **Assumed response time (ms)**.

The response-time assumption applies to the work in the round's iterations. It affects the estimated user lifetime and therefore how many users remain active when later users arrive. The headline shows the overall estimated peak and the estimated user lifetime where a finite lifetime is available.

Changing the assumption changes only the preview. It does not send traffic, change the target server's response time, or save a new plan setting.

### Stage Colors and Boundaries

Stage 1 uses amber, Stage 2 blue, and Stage 3 mint. The light bands on the plot, launch strip, and peak markers use matching stage colors.

The bands describe **launch windows**, not separate populations of active users. A user launched in Stage 2 can still be active during Stage 3. The curve remains continuous because it shows the total across those populations.

A subtle vertical line marks a stage's start. When adjacent stages have their peaks at the same boundary and the markers nearly coincide, the chart uses a split-color marker. Hovering either boundary peak shows both the ending and starting totals. Peaks farther apart remain separate points.

The stage table is informational. Stage names do not act as links or zoom controls.

### Understand the Stage Table

| Column | Meaning |
| --- | --- |
| **Stage** | The stage name and its first-to-last launch time. |
| **New users** | Users introduced by this stage. |
| **Peak total** | Estimated total active users at this stage's peak, including users still active from earlier stages. |
| **Peak at** | Time of that estimated peak, measured from the start of the round's preview. |

Do not add the stage peak totals together. They are observations at particular times, not independent user groups.

### Example: Why 400 and 401 Are Not 801 Users

Consider one request-count iteration with 200 requests per user and an assumed response time of 200 ms. With no additional delays, its estimated user lifetime is 40 seconds.

Use these stages:

| Stage | New Users | Arrival Delay | Launch Window | Peak Total | Peak At |
| --- | ---: | ---: | --- | ---: | ---: |
| Stage 1 | 100 | 100 ms | 0 to 9.9 s | 100 | 9.9 s |
| Stage 2 | 300 | 100 ms | 9.9 to 39.8 s | 400 | 39.8 s |
| Stage 3 | 1,000 | 200 ms | 39.8 to 239.6 s | 401 | 39.8 s |

At 39.8 seconds, 400 users are already active at the end of Stage 2's launches. The first Stage 3 user takes the total to 401. The shared boundary tooltip therefore reads:

```text
Stage transition at +39.8 s
Stage 2 ends: 400 total users
Stage 3 starts: 401 total users
```

The overall estimated peak is **401 concurrent users**, not 801. Although the plan introduces 1,400 users in total, they do not all remain active at the same time. Later, users finish and the curve falls even while Stage 3 continues launching users.

### Zoom and Dense Previews

Use **Zoom in**, **Zoom out**, **Earlier**, **Later**, and **Reset zoom** in the chart toolbar to inspect a period. The stage table and overall peak continue to describe the full preview while the plot is zoomed.

For a dense timeline, **min/max range** shows the minimum and maximum active-user counts within small time intervals. This is a compact rendering of the estimate, not a confidence interval or measured variability.

Very large previews may show **sampled points** instead. Sampling can miss short changes; zoom into a smaller interval to inspect more detail. The caption identifies the representation being used.

### Estimate Limitations

The estimate assumes a constant response time and includes the round's iterations. It is not a prediction of actual server capacity or an assertion that requests take that long in production.

Retries, watchdog pauses, hooks, skips, and early termination are not predicted. Cooldowns can keep users active without those users continuously sending requests. Open-ended cooldown-batch workloads use a configurable **Time after last launch (s)** preview horizon, not a promised finish time. An open-ended sequential user can prevent later users from launching.

If required numeric settings cannot be resolved, the chart reports that the estimate is unavailable. Review the settings and **Estimate assumptions**, then use measured run results to evaluate real behavior.

## Configure Rules

The Editor separates three types of conditions:

| Tab | Purpose |
| --- | --- |
| **Failure rules** | Define when test metrics represent a failed outcome. |
| **Termination rules** | Define when execution should stop early. |
| **Skip conditions** | Decide when work should be skipped. |

These are not interchangeable. A failed result is not necessarily an HTTP error, and skipped work is not a successful response. Check each rule's metric, comparison, and threshold before running a test.

For examples and semantics, see the [Beginner Guide](19.FAQs.md), [Migration Guide](10.MigrationGuide.md), and [SkipIf](16.SkipIf.md).

## Run and Monitor

Choose **Run test** when the plan is ready. If validation fails, the Editor identifies the affected configuration and directs you to the relevant field or tab.

The **Current run** area shows the run's state and output. Only one Workspace run can own the local runner at a time. Preparation, execution, stopping, and finalization are all part of that active lifecycle; a new run is not available merely because request generation has stopped.

Use the run's stop control to end that test. Allow finalization to complete before interpreting the retained result or starting another run.

During an active run, **Monitoring** opens the dashboard associated with that runner. Use this link instead of assuming the runner's dashboard uses the Workspace's port. The Workspace host and metrics dashboard have different roles.

The monitoring dashboard provides windowed and cumulative measurements. Windowed metrics describe recent intervals; cumulative metrics describe the run as a whole. Neither should be confused with the Editor's estimated active-user chart. See the [Dashboard guide](5.Dashboard.md) and [Timing Metrics](13.TimingMetrics.md) for interpretation.

## Review History

Open **History** to select a previous run. Each run has its own detail page, so you can return to a particular result without confusing it with the current editor draft.

A saved test and a historical run are different things. Editing a test prepares its next execution; it does not rewrite the result of an earlier run. Deleting a saved test keeps its run history.

Use retained output and metrics to review the outcome, HTTP failures, failed rules, and skipped requests. Host metrics are available when the run retained them; older runs without a host snapshot cannot display data that was never recorded.

The run detail view provides:

- **Results** for the recorded metrics and outcome.
- **Logs** for the run's captured output.
- **Download run results** to download the run details, logs, and metrics as JSON.
- **Use run snapshot** to load the plan captured for that execution into the Editor as the starting point for a new test.

Using a run snapshot does not overwrite the historical run. If the Editor has unsaved changes, resolve the discard confirmation before switching to that snapshot.

## Configure Engine Settings

Open **Settings** to edit the engine configuration. The page displays the configuration file it is updating and separates the available settings into six sections:

| Section | Controls |
| --- | --- |
| **Watchdog** | Memory, CPU, and per-host connection limits; recovery thresholds; cooling intervals; and whether any or all limits trigger suspension. |
| **HTTP Client** | Request timeout, pooled connection lifetime and idle timeout, maximum connections per server, header validation, and Host header override. |
| **Logging** | Log file path, file and console severity levels, and logging switches. |
| **Dashboard** | Default command-line dashboard port, refresh interval, and whether command-line runs open the dashboard. |
| **Live Metrics** | The metrics publish interval. |
| **InfluxDB** | Publishing switch, server URL, organization, bucket, and token management. |

**Save settings** saves changes across all six sections, not just the selected section. Changes apply to **new runs**; they do not reconfigure a test already running. **Revert** discards unsaved settings edits after confirmation. A validation error directs you to the affected setting, including settings in another section.

The Dashboard settings do not change the Workspace's `lps ui --port`. Workspace runs use an automatically selected runner dashboard port and do not automatically open another dashboard browser tab; use **Monitoring** when you need it.

An existing InfluxDB token is not displayed back in the form. Leave the token field unchanged to retain it, enter a replacement to update it, or use **Remove saved token** to clear it.

See [Watchdog](6.WatchDog.md), [HTTP Client Configuration](8.ClientConfiguration.md), [Logging](7.Logger.md), and [InfluxDB Integration](12.InfluxDBIntegration.md) for the underlying engine settings.

## Save Drafts and Work with Advanced Plans

Edits remain a draft until **Save** or **Run test** persists them. Switching between tabs or selected iterations does not automatically save the test. The GUI warns before discarding an unsaved plan, but browser warnings are not a substitute for saving.

Save before refreshing the page, closing the tab, or loading a different test. A chart-only preview adjustment is not a saved test change.

Use **Test actions** to duplicate, export, or delete a test. **Export YAML** and **Export JSON** download the saved plan as a `.yaml` or `.json` file. Both are unavailable until the test has been saved with no outstanding edits. Duplicating a test creates a new test draft; deleting one does not delete its run history. The currently running test cannot be deleted.

The visual form supports rounds with directly defined HTTP iterations in request-count (`R`) or duration (`D`) mode. Plans using batch modes (`CB`, `CRB`, or `DCB`), shared iteration references, top-level iterations, variables, or environments open as advanced plans.

Advanced plans retain their rounds and requests without exposing them to form editing. The test name, save, run, duplicate, and export actions remain available as applicable, while **Test API** is disabled. The GUI may still show a workload estimate for each round. An available estimate does not mean the whole plan is visually editable; use the plan's source representation and existing LPS authoring tools for changes to advanced structures.

Treat exported plans and downloaded run results as potentially sensitive. They can contain request URLs, headers, bodies, and captured output. Review and redact them before sharing.

## Troubleshooting

| Symptom | What to Check |
| --- | --- |
| The Workspace does not open | Check `lps ui --help`, the startup message, and the selected port. With `--open-browser false`, open the printed URL manually. |
| The port is already in use | Use another `--port`, or stop the appropriate existing UI host. LPS does not treat an unrelated process on that port as its Workspace. |
| The host starts but the page is missing | Check that the build includes its frontend assets. A custom `--webroot` must point to the built frontend directory. |
| The connection indicator stays on Connecting | Confirm that the local Workspace host is still running and the browser is using its URL. |
| Test API or Run test is unavailable | Check the connection, whether another operation or run is active, and whether the selected plan supports the visual workflow. |
| Save or Run test reports validation errors | Review the indicated round, iteration, tab, and field. Required settings may be outside the currently visible tab. |
| The estimate differs from the measured run | Review the assumed response time, iteration modes, and estimate limitations. Use measured results for performance conclusions. |
| The new UI is not visible after an update | Save your draft, then refresh the Workspace page. |

Background host output is written to `ui-<port>.log` in the selected Workspace data directory. The default port uses `ui-8010.log`.
