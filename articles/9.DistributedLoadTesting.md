# LPS Distributed Load Testing

LPS supports two master/worker workflows. Use your own JSON or YAML plan and an endpoint you are authorized to test. No separate JavaScript server or bundled demo plan is required; LPS does not require Node.js.

Install the **same updated LPS build on every machine**. The new workflow requires a build containing the `worker` command; an older installed package may not include it. Commands below use the installed `lps` executable.

## Choose A Workflow

| Behavior | New: Persistent Workers | Legacy |
| --- | --- | --- |
| Worker command | `lps worker` | `lps run <plan>` |
| Master command | `lps master <plan> --workers <count>` or `--settings <path>` | Bare `lps master <plan>`, or `lps run <plan>` |
| Startup order | Start worker agents, then master | Start master and wait for readiness, then workers |
| Plan location | Master transfers the plan to workers | Same plan must be provided on every node |
| Execution | Fresh child process per run; agent stays alive | Worker process executes its local plan, then exits |
| Start coordination | All selected executors must be prepared before planned load starts | Workers may start when the master is Ready/Running; no all-workers-ready barrier |
| Remote cluster transport | HTTPS with registration token and server certificates | Existing unauthenticated HTTP; trusted isolated networks only |
| Worker listener | Explicit `--listen` or automatic IP/port | Explicit `run --listen` or automatic IP/port |

Do not mix persistent agents with a legacy master or legacy workers with a new master. Each executor runs the **whole plan**; request/client counts are not divided among workers.

## Cluster Settings

The examples use these addresses. Replace them with your machines' reachable addresses:

| Node | IP | Fixed Callback Port |
| --- | --- | --- |
| Master | `192.168.1.10` | `5161` |
| Worker 1 | `192.168.1.11` | `5162` |
| Worker 2 | `192.168.1.12` | `5163` |

On **every machine**, configure the same master address and external worker count:

```powershell
lps cluster --masternodeip 192.168.1.10 --masternodeport 5161 --expectednumberofworkers 2 --masternodeisworker false
```

This updates `LPSAppSettings.Cluster` in the application's settings. The corresponding section is:

```json
{
  "MasterNodeIP": "192.168.1.10",
  "MasterNodePort": 5161,
  "ExpectedNumberOfWorkers": 2,
  "MasterNodeIsWorker": false
}
```

Merge this section into your existing settings; do not replace the entire settings file with this fragment. Keep your HTTP, watchdog, dashboard, logging, and exporter settings. Run-time source settings are not rewritten by a test.

| Setting | Meaning |
| --- | --- |
| `MasterNodeIP` | Master connection address. Use a plain IP for settings shared with legacy. In the new workflow a full HTTP(S) URL can supply its own scheme/port; plain remote hosts use HTTPS and loopback uses HTTP. |
| `MasterNodePort` | Master listener port, not a shared worker port. |
| `ExpectedNumberOfWorkers` | External agents required by the new workflow. Legacy dedicated masters wait for at least this many registrations, with a minimum of one. |
| `MasterNodeIsWorker` | New master: add an owned local agent and executor. Legacy `run` on the master: execute locally immediately. Bare legacy `master` stays dedicated. |

Existing `GRPCPort` settings remain valid. If both port names exist, **`MasterNodePort` wins**, regardless of property order. `lps cluster --grpcport 5161` and `lps cluster -gp 5161` remain aliases for `--masternodeport 5161`.

To use a separate, complete settings file, set this in each terminal **before** running configuration or execution commands:

```powershell
$env:LPS_SETTINGS_FILE = 'C:\LPS\cluster.json'
```

Explicit new-workflow flags override saved values, including explicit `false`. With no cluster section, the new master defaults to one external worker and no local executor. A configured section with an omitted worker count inherits the options default of zero, so set the intended count explicitly.

## Network And Credentials

Allow these connections through your host/network firewalls:

- Workers to the master's TCP port `5161` for registration, control streams, and worker-pushed metrics.
- Master to each worker's callback port (`5162` / `5163` in these examples) for control and execution-status queries.
- Each executor to the target endpoints and dependencies in your plan.

Prefer fixed worker ports for predictable firewall rules. Automatic ports require a suitable, peer-restricted application rule or other administrator-approved network policy. LPS does not change firewall or NAT rules. A worker's successful outbound registration does not prove its inbound callback address is reachable.

### New Workflow Credentials

Provision a server PFX on every node and the public cluster CA PEM when using a private CA. The certificate SAN must cover that node's advertised IP or DNS name. The examples assume `C:\certs\master.pfx`, `worker1.pfx`, or `worker2.pfx` on the respective machine, and `C:\certs\ca.pem` on all nodes. Protect private keys and do not disable certificate validation.

Generate a private registration token **once** on a trusted machine, or obtain it from your secret-management system. For example, with an existing private `C:\certs` directory:

```powershell
$bytes = New-Object byte[] 32
$random = [Security.Cryptography.RandomNumberGenerator]::Create()
$random.GetBytes($bytes)
$random.Dispose()
[IO.File]::WriteAllText('C:\certs\cluster-token.txt', [Convert]::ToBase64String($bytes))
```

Securely distribute the **same token** to every node. Do not regenerate it independently on each machine or overwrite a token while the cluster is running. Restrict token/PFX files to the account running LPS; do not put them in Git or paste their contents into chat.

In each node's LPS terminal:

```powershell
$env:LPS_CLUSTER_TOKEN = (Get-Content C:\certs\cluster-token.txt -Raw).Trim()
$env:LPS_CLUSTER_CERT_PASSWORD = [Net.NetworkCredential]::new('', (Read-Host 'PFX password' -AsSecureString)).Password
```

The token must be at least 32 characters with no whitespace. The password is passed to LPS through the process environment, not as a CLI argument. A publicly trusted certificate does not require `--ca-cert`. These credentials secure the **cluster transport**, independently of any credentials your plan needs for its load target. Legacy does not use these token/certificate options.

## New Approach: Persistent Workers

### 1. Start Worker Agents

Worker 1:

```powershell
lps worker --name worker-1 --listen https://192.168.1.11:5162 --certificate C:\certs\worker1.pfx --ca-cert C:\certs\ca.pem --data-directory C:\LPS\worker-1
```

Worker 2:

```powershell
lps worker --name worker-2 --listen https://192.168.1.12:5163 --certificate C:\certs\worker2.pfx --ca-cert C:\certs\ca.pem --data-directory C:\LPS\worker-2
```

The master address comes from the saved settings. To override it, append `--master https://192.168.1.10:5161`. Every agent needs a unique name and data directory. Agents can wait and retry while the master is absent; no plan argument is needed.

**Automatic worker address and port:** omit `--listen` and its value. Use these instead of the fixed-port commands, not alongside them:

```powershell
# Worker 1 machine
lps worker --name worker-1 --certificate C:\certs\worker1.pfx --ca-cert C:\certs\ca.pem --data-directory C:\LPS\worker-1

# Worker 2 machine
lps worker --name worker-2 --certificate C:\certs\worker2.pfx --ca-cert C:\certs\ca.pem --data-directory C:\LPS\worker-2
```

For a remote master, the worker detects its local IP and uses HTTPS plus an automatic port. Its certificate must cover that detected IP. `--listen https://192.168.1.11:0` fixes the IP while selecting the port automatically. Use explicit DNS/IP listeners for multiple network interfaces or NAT. The option is **`--listen`**, not `--listener`.

### 2. Start The Master With Your Plan

On the master, with your plan at `C:\LPS\plan.yaml`:

```powershell
lps master C:\LPS\plan.yaml --workers 2 --listen https://192.168.1.10:5161 --masternodeisworker false --certificate C:\certs\master.pfx --ca-cert C:\certs\ca.pem --registration-timeout 120 --data-directory C:\LPS\master
$LASTEXITCODE
```

Or use your complete settings copy for the address/count instead of repeating those flags:

```powershell
lps master C:\LPS\plan.yaml --settings C:\LPS\cluster.json --certificate C:\certs\master.pfx --ca-cert C:\certs\ca.pem --registration-timeout 120 --data-directory C:\LPS\master
```

The master transfers the plan, waits for all selected executors to be ready, then starts the run. After finalization it prints the result path and exits; agents stay available. Repeat **only the master command** for another run.

### 3. Optional Master Participation

Two external workers plus an owned local executor:

```powershell
lps master C:\LPS\plan.yaml --workers 2 --listen https://192.168.1.10:5161 --masternodeisworker true --certificate C:\certs\master.pfx --ca-cert C:\certs\ca.pem --registration-timeout 120 --data-directory C:\LPS\master
```

The local executor participates in the same readiness barrier and uses its own automatic callback port. The name `master-local` is reserved. `--workers` still counts only **external** agents. Local-only execution uses `--workers 0 --masternodeisworker true`; zero total executors is rejected.

For example, a plan containing one iteration of 10 requests with one client produces 20 planned requests on two executors, or 30 on three. Warm-up and connection probes can add target traffic beyond the planned requests.

## Legacy Approach: Master First

Stop any persistent cluster before switching workflows. Provide the same plan on every machine and use the plain master IP in the shared cluster settings. Legacy role detection compares the detected local IP to `MasterNodeIP`; on a multi-NIC master, use the matching IP or the explicit legacy `run --listen` alternative below.

### 1. Start A Dedicated Master

On the master, start this command first and wait for `Master node is ready`:

```powershell
lps master C:\LPS\plan.yaml
```

Bare `master` always coordinates without generating load, even if `MasterNodeIsWorker` is true. **Do not append `--workers`, `--listen`, `--settings`, or `--masternodeisworker` (`-miw`) to this command: those select the new workflow.** Legacy obtains its settings from the default file or `LPS_SETTINGS_FILE`.

### 2. Run The Workers

For automatic addresses and ports, run on **each worker machine**:

```powershell
lps run C:\LPS\plan.yaml
```

Or use fixed ports for predictable firewall rules:

```powershell
# Worker 1 machine
lps run C:\LPS\plan.yaml --listen http://192.168.1.11:5162

# Worker 2 machine
lps run C:\LPS\plan.yaml --listen http://192.168.1.12:5163
```

The worker prints `Node endpoint: http://<ip>:<port>`, then sends the full endpoint in its existing `RegisterNode` gRPC call. Automatic ports are assigned by the OS when the listener binds; registration happens after binding. `MasterNodePort` tells workers where to connect to the master, not where to listen themselves.

Legacy workers may begin as soon as they see the master Ready/Running. `ExpectedNumberOfWorkers` does **not** provide the new preparation barrier. After execution, worker processes exit; for the next run restart the master and then the worker commands.

### 3. Alternative Legacy Master Commands

With `MasterNodeIsWorker` set to false, `run` also supports a dedicated master and allows an explicit local address:

```powershell
lps cluster --masternodeisworker false
lps run C:\LPS\plan.yaml --listen http://192.168.1.10:5161
```

To make the legacy master execute load too:

```powershell
lps cluster --masternodeisworker true
lps run C:\LPS\plan.yaml --listen http://192.168.1.10:5161
```

This starts master-side execution immediately instead of waiting for every worker. A short plan can finish before workers join. Use the new workflow for coordinated master participation; do not treat absent workers as successful participants. Restore the setting to false before repeating the dedicated-master baseline.

## Metrics, Results, And Shutdown

Workers **push iteration and host metrics to the master**. The master aggregates them and uses worker endpoints for control and execution-status callbacks, not polling metric values. In the new workflow, plan transfer uses the worker-initiated control stream.

The new master writes results in its private run directory:

```powershell
Get-ChildItem C:\LPS\master -Recurse -Filter cluster-result.json
```

Inspect the latest overall `State`, exit code, and final cumulative metrics under that run's `Metrics` directory. Metric filenames reflect your plan's iteration names. Worker `Completed` means execution finished; the master decides the aggregate failure-rule verdict. Compare actual target responses and metrics, not only exit codes. Plain legacy commands do not create the new run-result manifest or automatically persist the same final metrics files; some legacy failures are logged without a nonzero exit code.

When enabled through `Dashboard.BuiltInDashboard`, the master hosts the dashboard. New-workflow workers remain headless; the new dashboard uses a separate loopback HTTP listener, even when cluster gRPC uses HTTPS. Use it on the master machine, or an appropriately secured tunnel. `--dashboard-port 8110` chooses a fixed new-master dashboard port. With the dashboard enabled, final refresh waits for two polling intervals (at least 10 seconds) before shutdown; after the master exits the loaded page remains, but refresh/navigation fails.

- Cancel using Ctrl+C in the master terminal, then verify its workers stop executing.
- Stop idle persistent agents with Ctrl+C in each agent's own terminal. Never blanket-kill `dotnet` processes.
- Edit the source plan for the next run, not archived run copies. Keep worker run claims so old assignments cannot be replayed.
- For a new-workflow missing-worker check, use `--registration-timeout 5`; expect failure without planned load. Legacy has no equivalent all-workers-ready guarantee.
- After stopping the processes, clear credentials from the terminal:

```powershell
Remove-Item Env:LPS_CLUSTER_TOKEN,Env:LPS_CLUSTER_CERT_PASSWORD,Env:LPS_SETTINGS_FILE -ErrorAction SilentlyContinue
```

## Compatibility And Limits

- Existing `GRPCPort` settings and `--grpcport` / `-gp` flags remain accepted. Generated private settings use the preferred `MasterNodePort` name.
- Legacy node metadata adds an optional callback endpoint, preserving existing protobuf field numbers and IP/name identity. Updated master callbacks prefer that endpoint; older IP-only metadata falls back to host plus the configured master port. This is not a guarantee that mixed old/new binaries support automatic ports; update all nodes together.
- Persistent automatic ports are selected before execution-child binding, so a competing bind can cause preparation to fail. No planned load starts on preparation failure. Automatic detection does not solve certificate SAN, routing, firewall, or NAT configuration.
- Only the plan is transferred, limited to 1 MiB. Provision referenced data, certificates, and other dependencies on the relevant nodes. Relative paths resolve inside private run directories. Persistent commands do not accept the legacy round/tag/environment selection flags.
- A dropped connection or expired heartbeat lease cancels its run. There is no automatic run resume/replay or durable master recovery; start a new explicit run after interruption.
- Plans, authenticated workers, and advertised callback endpoints are trusted inputs. Process isolation is not a permission sandbox. Run/settings copies and logs can contain credentials; keep them private. Do not expose the cluster as a public multi-tenant service.

## Verification

The implementation passed 536 .NET tests on Windows, including 25 independent-process cases: 21 persistent-workflow and four legacy cases. Coverage includes port-name compatibility, fixed/automatic worker listeners, callback routing, exact aggregate request counts, TLS/authentication, readiness, cancellation, process loss, and master participation. A separate published-build smoke check also passed.

These are local checks, not proof of LAN/WAN routing, firewall/NAT policy, certificate deployment, clock skew, or Linux/macOS behavior. Start manual deployment testing with a small plan against your own controlled endpoint, then inspect the results before increasing load.
