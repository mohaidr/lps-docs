# Breakpoint Testing (Capacity Testing)

A **breakpoint test** (also known as a *capacity*, *limit*, or *point-load* test) gradually ramps load toward a very high ceiling—with **no intermediate plateaus**—until response times or error rates breach your limits and automatically stop the run.

Run breakpoint tests after your service already passes [Smoke](21.SmokeTesting.md), [Load](22.LoadTesting.md), and [Stress](23.StressTesting.md) tests and you want to find the **exact upper limit** of your current architecture.

---

## What a Breakpoint Test Answers

- **Maximum SLA capacity:** How many concurrent clients and requests per second can the system sustain before `P95` latency or `5xx` errors cross acceptable bounds?
- **First bottleneck:** Which component saturates first as traffic climbs continuously—CPU, database connections, lock contention, network bandwidth, or upstream rate limits?
- **Tuning impact:** After optimizing queries, caching, or thread pools, how much higher did the breaking point move when repeating the exact same ramp?

---

## How to Structure a Breakpoint Test in LPS

In LPS, a breakpoint test needs **only one round** (no `stages` required) combining three settings:

1. **Large `numberOfClients` + gradual `arrivalDelay`:** For example, `3000` clients with `arrivalDelay: 600` ms adds **100 clients per minute** over a smooth 30-minute (`1800`-second) climb—slow enough to pinpoint the exact concurrency where degradation starts.
2. **`mode: D` with `duration` slightly longer than the ramp:** Setting `mode: D` with `duration: 2100` seconds (**35 minutes** per client—5 minutes longer than the 30-minute ramp) lets each client send sequential requests as fast as the server responds, keeps Client #1 active throughout the entire 30-minute climb, **and** ensures the test finishes cleanly on its own (`30m ramp + 35m duration = 1h 05m` max) if the server survives all 3,000 clients.
3. **`terminationRules` as the automatic brake:** Stops the climb automatically as soon as error rate or tail latency stays breached for its `gracePeriod`, while `failureRules` grade the run if the full 3,000-client ceiling completes without tripping termination.

> **Choosing the iteration mode:**
> - **`mode: D` *(recommended default)*:** Sequential requests with no artificial delay and a safe upper `duration` cap (`Max run time = Ramp time + duration`) so the test finishes automatically if the ceiling is survived.
> - **`mode: DCB`:** Same safe `duration` cap when sending recurring request batches separated by a `coolDownTime` between batches.
> - **`mode: CB` *(optional, supervised only)*:** Removes the `duration` cap completely so active clients keep running indefinitely until `terminationRules` fire or you stop the run manually (`Ctrl+C`).

## Runnable YAML Breakpoint Test Plan

**Example assumptions:** up to 3,000 clients are authorized, one new client joins every 600 ms (100 clients/minute over 30 minutes), each client runs sequential requests for up to 35 minutes (`mode: D`, `duration: 2100`), and `terminationRules` abort the climb once `5xx` errors exceed `15%` or `P95` exceeds `3000` ms for 15 seconds.

```yaml
name: ContinuousRampBreakpointTest
variables:
- name: targetUrl
  value: https://api.example.com/resource
rounds:
- name: LinearRampToBreakpoint
  numberOfClients: 3000
  arrivalDelay: 600
  iterations:
  - name: BreakpointResource
    mode: D
    duration: 2100
    httpRequest:
      url: $targetUrl
      httpMethod: GET
    failureRules:
    - metric: "ErrorRate > 0.05"
      errorStatusCodes: ">= 500"
    - metric: "TotalTime.P95 > 1500"
    terminationRules:
    - metric: "ErrorRate > 0.15"
      errorStatusCodes: ">= 500"
      gracePeriod: "00:00:15"
    - metric: "TotalTime.P95 > 3000"
      gracePeriod: "00:00:15"
```

Run the plan with:

```bash
lps run ContinuousRampBreakpointTest.yaml
```

---

## Reading the True Breaking Point

- **Account for the `gracePeriod` window:** With `arrivalDelay: 600` ms and `gracePeriod: "00:00:15"`, roughly **25 additional clients** (`15s / 0.6s`) spawn while LPS confirms the breach is sustained. Inspect the live dashboard or Grafana windowed charts ~15 seconds before termination to read the exact concurrency and RPS where degradation started.
- **If the server survives all 3,000 clients:** Because each client's 35-minute clock starts when it spawns, Client #1 finishes at `35:00` (giving a 5-minute 3,000-client peak from `30:00–35:00`) and Client #3000 finishes at `1:05:00`, evaluating `failureRules` and telling you the breaking point sits above 3,000 clients.

---

## Important Considerations

- **Disable cloud autoscaling first:** Running a breakpoint test against an unconstrained auto-scaling cluster only measures your cloud billing limit. Lock the instance/pod count first so you measure the true capacity of a known footprint, then scale out deliberately.
- **Ramp gradually, not instantly:** Keep `arrivalDelay` smooth (`200–1000` ms depending on ceiling size); ramping too fast turns a breakpoint search into a [Spike Test](24.SpikeTesting.md) and makes it hard to pinpoint the exact concurrency where degradation began.
- **Ensure load-generator headroom:** For multi-thousand-client ceilings, monitor generator CPU/sockets with `lps watchdog` or distribute load across worker machines using [Distributed Load Testing](9.DistributedLoadTesting.md).
