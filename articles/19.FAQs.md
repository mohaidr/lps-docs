# LPS Beginner Guide: Common Questions and Practical Answers

This guide answers the questions most new LPS users ask. Start with the quick test, learn the execution model, and then move to larger or more advanced plans.

> **Safety first:** Run load tests only against systems you own or are explicitly authorized to test. Begin with a small number of clients and requests, observe the target system, and increase load gradually.

---

## 1. What is LPS?

LPS is a cross-platform command-line tool for load, performance, and stress testing web applications and APIs.

It helps you answer questions such as:

- How many users or requests can this service handle?
- How does response time change as traffic increases?
- When do errors begin to appear?
- Does the system recover after a traffic spike?
- Which test result should fail a release?
- When should a damaging test stop automatically?

LPS can run a quick test directly from the command line or execute a reusable YAML plan. A plan combines five main concepts:

1. **Clients** represent independent virtual users or traffic sources.
2. **Rounds** divide the test into sequential phases.
3. **Iterations** describe the work each client performs.
4. **Iteration modes** control the request count, duration, or burst pattern.
5. **Rules** evaluate the result or stop an unhealthy test.

---

## 2. What do I need before installing LPS?

Install the .NET 8 SDK before installing LPS as a global tool. LPS works on Windows, Linux, and macOS.

Install LPS as a global .NET tool:

```bash
dotnet tool install --global lps
```

Confirm that it is available:

```bash
lps --version
```

If the command is not found immediately after installation, restart the terminal so it reloads the global .NET tools path.

---

## 3. What is the fastest way to run my first test?

Use a quick command when you want to test one endpoint without creating a plan file.

Send 10 GET requests:

```bash
lps --url https://www.example.com -rc 10
```

Start five clients gradually, with 1,000 milliseconds between client arrivals:

```bash
lps --url https://www.example.com --numberofclients 5 --arrivaldelay 1000 -rc 10
```

For a first test, use a safe non-production endpoint, a low client count, and a low request count. Confirm the result before increasing the load.

---

## 4. When should I use a YAML plan instead of a quick command?

Use a YAML plan when the test must be repeatable, reviewed, stored in source control, or expanded beyond one simple request.

A plan is the better choice when you need:

- Multiple endpoints or user actions
- Several test phases
- Variables and environments
- Authentication or captured response data
- Failure or termination rules
- Repeatable team or CI/CD execution
- Distributed load generation

Quick commands are useful for exploration. YAML plans are better for tests that matter.

---

## 5. How do I create my first LPS plan?

Create a file named `first-plan.yaml` with this content:

```yaml
name: FirstPlan
rounds:
- name: FirstRound
  numberOfClients: 20
  arrivalDelay: 1000
  iterations:
  - name: HomePage
    mode: R
    requestCount: 50
    httpRequest:
      url: https://www.example.com
      httpMethod: GET
```

Run it with:

```bash
lps run first-plan.yaml
```

You can also build the same plan incrementally with LPS commands:

```bash
lps create first-plan.yaml --name FirstPlan
lps round first-plan.yaml --name FirstRound --numberofclients 2 --arrivaldelay 1000
lps iteration first-plan.yaml --roundname FirstRound --name HomePage --iterationmode R --requestcount 5 --url https://www.example.com --httpmethod GET
```

Editing YAML directly is usually easier when learning because the complete plan structure remains visible. The commands are useful when generating or modifying plans from scripts.

LPS can also create a starting plan by [recording browser traffic](https://github.com/mohaidr/lps-docs/blob/main/articles/18.Record.md). This is useful when you want to capture an existing user workflow instead of entering each request manually. See the next question for details.

What this plan does:

- Creates two clients.
- Starts them one second apart.
- Each client performs the `HomePage` iteration.
- Each client sends five sequential GET requests.
- The plan therefore schedules 10 primary requests in total: 2 clients x 5 requests.

Retries, skipped requests, cancellation, or early termination can change the number of requests actually sent.

## 6. Can LPS create a test plan by recording browser traffic?

Yes. The `record` command opens a Chromium browser, captures HTTP traffic while you browse an application, and converts the captured requests into a starting LPS plan in YAML or JSON format.

Install the browser once:

```bash
lps record --install
```

Then record a workflow:

```bash
lps record app.yaml --url https://www.example.com --only-host example.com
```

Browse the workflow you want to test, then close the browser or press Enter in the terminal. LPS filters the captured traffic and writes the plan. It uses Playwright HAR capture, so it does not require a proxy or root certificate.

The generated plan is a starting draft. Before running it at scale:

- Remove unnecessary requests and headers.
- Replace cookies, tokens, and other secrets with variables.
- Parameterize dynamic IDs and captured values.
- Configure the clients, arrival delay, iteration modes, and rules.
- Run a small smoke test first.

Use `--append` to add another recorded flow to an existing plan, or `--update` to refresh matching requests without duplicating them.

## 7. What is the basic structure of an LPS plan?

The plan is the YAML document root. Do not add a `plan:` wrapper.

```yaml
name: MyTestPlan
variables:
- name: apiUrl
  value: https://api.example.com
rounds:
- name: LoadRound
  numberOfClients: 10
  arrivalDelay: 1000
  iterations:
  - name: GetResource
    mode: R
    requestCount: 20
    httpRequest:
      url: ${apiUrl}/resource
      httpMethod: GET
```

The hierarchy is:

```text
Plan
|-- Variables and environments
`-- Rounds
    `-- Clients
        `-- Iterations
            `-- HTTP requests
```

YAML is indentation-sensitive, and LPS field names use camelCase. For example, use `httpRequest`, not `httprequest` or `http_request`.

## 8. How do I run a plan?

Run the complete plan:

```bash
lps run first-plan.yaml
```

Run one named round:

```bash
lps run first-plan.yaml --roundname FirstRound
```

Run rounds with a selected tag:

```bash
lps run first-plan.yaml --tag smoke
```

Run with a named environment:

```bash
lps run first-plan.yaml --environment staging
```

Before a large test, check the file with a YAML linter and run a small smoke test against an authorized environment.

## 9. How does LPS execute a plan?

The normal execution flow is:

1. LPS reads the YAML plan and resolves its configuration.
2. Rounds run in the order in which they are defined.
3. For a round, LPS schedules its clients using `numberOfClients` and `arrivalDelay`, or its configured stages.
4. Each client begins work when its arrival time is reached.
5. Each client runs the round's iterations sequentially by default.
6. The iteration mode controls how each client sends requests.
7. LPS collects live cumulative and windowed metrics during execution.
8. Termination rules are evaluated continuously.
9. Failure rules are evaluated after an iteration completes.
10. The round finishes after its clients complete, and then the next round starts.

If `runInParallel: true` is configured on the round, its iterations can execute in parallel instead of sequentially. Use that setting only when parallel behavior matches the real workflow you want to simulate.

---

## 10. What is a client?

A client is an independent virtual user or traffic source.

`numberOfClients` controls how many clients enter a round. `arrivalDelay` controls the delay, in milliseconds, between their start times.

```yaml
numberOfClients: 5
arrivalDelay: 1000
```

This starts five clients one second apart. It does not start all five simultaneously.

The first client starts immediately. The fifth client starts approximately four seconds after the first. Once started, clients can run concurrently.

Depending on the scenario, a client can represent an end user, a device, a worker, a gateway, or another independent traffic source.

---

## 11. What is a round?

A round is a major phase of a test. Rounds always run sequentially.

Typical rounds include warm-up, baseline, expected load, peak load, stress, and recovery.

```yaml
rounds:
- name: WarmUp
  numberOfClients: 2
  arrivalDelay: 1000
  iterations:
  - name: HealthCheck
    mode: R
    requestCount: 5
    httpRequest:
      url: https://api.example.com/health
      httpMethod: GET
- name: ExpectedLoad
  numberOfClients: 20
  arrivalDelay: 500
  iterations:
  - name: Search
    mode: D
    duration: 120
    httpRequest:
      url: https://api.example.com/search?q=test
      httpMethod: GET
```

`ExpectedLoad` begins only after the clients in `WarmUp` have completed.

---

## 12. What is an iteration?

An iteration defines the work performed by each client inside a round.

It normally contains:

- A unique name
- An iteration mode
- The count, duration, batch, or cooldown settings required by that mode
- An HTTP request
- Optional conditions and rules

```yaml
- name: GetProduct
  mode: R
  requestCount: 20
  httpRequest:
    url: https://api.example.com/products/1
    httpMethod: GET
```

If a round contains `Login`, `Browse`, and `Checkout` iterations, every client normally executes them in that order. This makes iterations suitable for modeling a user journey.

---

## 13. What is the difference between a round and an iteration?

- A **round** is a test phase that controls clients and their arrival pattern.
- An **iteration** is an action or workload performed by those clients.

For example:

- Round: `PeakTraffic`
- Clients: 100 shoppers arriving gradually
- Iteration 1: `BrowseProducts`
- Iteration 2: `AddToCart`
- Iteration 3: `Checkout`

Use a new round when the test phase, traffic population, or workload needs to be separated. Use another iteration when the same clients need to perform another action.

---

## 14. What iteration modes are available?

| Mode | Required settings | Behavior | Good use case |
|---|---|---|---|
| `R` | `requestCount` | Each client sends a fixed number of sequential requests | Smoke tests and exact request counts |
| `D` | `duration` | Each client sends sequential requests for a fixed number of seconds | Steady load and endurance tests |
| `DCB` | `duration`, `batchSize`, `coolDownTime` | Each client sends a batch, waits, and repeats for a duration | Recurring traffic bursts |
| `CRB` | `requestCount`, `batchSize`, `coolDownTime` | Each client sends batches with pauses until its request count is reached | A fixed amount of burst traffic |
| `CB` | `batchSize`, `coolDownTime` | Each client sends batches with pauses until manually stopped or terminated | Open-ended stress testing |

Choose the simplest mode that reproduces the traffic pattern you need.

---

## 15. Does `requestCount` apply to the whole test or to each client?

`requestCount` applies to each client executing that iteration.

```yaml
numberOfClients: 10
iterations:
- name: Search
  mode: R
  requestCount: 100
```

This schedules up to 1,000 primary requests: 10 clients x 100 requests.

This simple multiplication applies when there is one iteration and no skips, retries, cancellation, or early termination. Always calculate the expected load before running the test.

---

## 16. Does `duration` apply to the whole round or to each client?

`duration` applies to each client's execution of the iteration.

```yaml
numberOfClients: 50
arrivalDelay: 200
iterations:
- name: Browse
  mode: D
  duration: 300
```

The first client can run for 300 seconds. The final client starts about 9.8 seconds later and can then run for its own 300-second window. The round can therefore last approximately 310 seconds, plus any additional startup or processing overhead.

This distinction is important when estimating test duration and total traffic.

---

## 17. How do I create a gradual ramp-up or a traffic spike?

Use `stages` when you need several client levels inside one round. Stages override the round-level `numberOfClients` and `arrivalDelay`.

```yaml
name: RampUpPlan
rounds:
- name: RampUpRound
  stages:
  - numberOfClients: 5
    arrivalDelay: 1000
  - numberOfClients: 20
    arrivalDelay: 500
    startupDelay: 3000
  - numberOfClients: 50
    arrivalDelay: 200
    startupDelay: 3000
  iterations:
  - name: Search
    mode: D
    duration: 120
    httpRequest:
      url: https://api.example.com/search?q=test
      httpMethod: GET
```

Stages are processed in order, but they do not wait for earlier clients to complete. Earlier clients can still be running while later stages add more clients.

Use stages to vary concurrency for the same workload. Use separate rounds when you need independent phases or different iterations.

---

## 18. How do I send headers and a JSON payload?

```yaml
- name: CreateOrder
  mode: R
  requestCount: 10
  httpRequest:
    url: https://api.example.com/orders
    httpMethod: POST
    headers:
      Content-Type: application/json
      Authorization: Bearer ${accessToken}
    payload:
      type: Raw
      raw: |
        {
          "productId": "123",
          "quantity": 1
        }
```

Do not commit real passwords, tokens, or private keys to a plan file. Supply secrets through an approved secure mechanism for your environment.

Avoid `saveResponse: true` during high-load tests unless the response files are genuinely required. Saving every response can consume disk space and affect the load generator's performance.

## 19. How do variables work?

Define reusable values in the plan's `variables` section and reference them with `$name` or `${name}`.

```yaml
name: VariablePlan
variables:
- name: apiUrl
  value: https://api.example.com
- name: userId
  value: $randomnumber(min=1, max=100)
rounds:
- name: UserRound
  numberOfClients: 2
  arrivalDelay: 1000
  iterations:
  - name: GetUser
    mode: R
    requestCount: 5
    httpRequest:
      url: ${apiUrl}/users/${userId}
      httpMethod: GET
```

Variable resolution checks session variables first and then global variables. Variables declared in the plan-level `variables` section are global. Captured response variables are session-scoped by default, which keeps one client's data separate from another client's data.

---

## 20. What are declarative methods, and when should I use them?

Declarative methods are built-in `$...` expressions that generate, transform, read, or store values at runtime without custom scripts. They can be used as variable values or directly inside URLs, headers, and payloads.

```yaml
variables:
- name: requestId
  value: $guid()
- name: userId
  value: $randomnumber(min=1, max=100)

httpRequest:
  url: https://api.example.com/users/${userId}
  httpMethod: GET
  headers:
    X-Request-ID: ${requestId}
```

Common uses include:

- Generating unique or varied data with `$guid()`, `$random()`, `$randomnumber()`, or `$generateemail()`
- Creating timestamps with `$timestamp()` or `$datetime()`
- Reading values from environment variables or files with `$read()`
- Encoding, hashing, or signing values with `$base64encode()`, `$hash()`, `$hmac()`, or `$jwtsign()`
- Finding values in JSON or XML with `$find()` or `$findxml()`
- Transforming strings, performing calculations, and storing values for later requests

Use declarative methods when the required behavior is available as a built-in expression. Use a script only when the scenario needs custom logic that the built-in methods cannot express.

## 21. How do I capture a response and use it in the next request?

Use `capture` to store a response. Later requests can access its body, status code, reason, and headers.

```yaml
name: UserFlow
rounds:
- name: Workflow
  numberOfClients: 2
  arrivalDelay: 1000
  iterations:
  - name: GetUser
    mode: R
    requestCount: 1
    httpRequest:
      capture:
        to: userResponse
        as: Json
      url: https://jsonplaceholder.typicode.com/users/1
      httpMethod: GET
  - name: GetAlbums
    mode: R
    requestCount: 5
    skipIf: ${userResponse.StatusCode} != 200
    httpRequest:
      url: https://jsonplaceholder.typicode.com/users/${userResponse.Body.id}/albums
      httpMethod: GET
```

Because capture is session-scoped by default, each client uses its own `userResponse`. Use `makeGlobal: true` only when the value must be shared across all clients or rounds.

---

## 22. What does `skipIf` do?

`skipIf` prevents work from running when its expression evaluates to `true`.

At iteration level, it skips the iteration. At `httpRequest` level, it skips only that request.

```yaml
skipIf: ${loginResponse.StatusCode} != 200
```

This is useful for dependent workflows. For example, do not execute a checkout request if login failed.

If many requests are skipped unexpectedly, inspect the captured values and the `skipIf` expression. The dashboard's `SkipRatio` helps show how much planned work was skipped.

## 23. What is the difference between failure rules and termination rules?

| Concern | `failureRules` | `terminationRules` |
|---|---|---|
| Evaluation time | After the iteration completes | Continuously during execution |
| Effect | Mark the completed iteration as failed or successful; it does not stop the iteration while it is running | Terminate the running iteration when a configured threshold is reached and remains violated for the grace period |
| Grace period | Not used | Used for metric rules |
| Typical use | Evaluate final SLA targets and release criteria | Stop the test early when the target system exceeds an agreed safety limit |

Example:

```yaml
failureRules:
- metric: "TotalTime.P95 > 500"
- metric: "ErrorRate > 0.01"
  errorStatusCodes: ">= 500"
terminationRules:
- metric: "ErrorRate > 0.05"
  gracePeriod: "00:00:10"
  errorStatusCodes: ">= 500"
```

In this example, the failure rules wait until the iteration finishes and then evaluate its final metrics. They mark the result as failed if P95 exceeds 500 milliseconds or the selected error rate exceeds 1%, but they do not interrupt the running iteration.

The termination rule monitors the selected error rate while the iteration is running. If the error rate remains above 5% for 10 continuous seconds, LPS terminates that iteration early. If the error rate returns to 5% or below before the grace period ends, the iteration continues.

Status code `0` represents connectivity failures such as DNS errors, connection refusal, timeouts, TLS failures, or an unreachable network.

## 24. Which metrics should a beginner watch?

Start with these metrics:

- `Throughput.RPS`: completed requests per second
- `ErrorRate`: proportion of requests counted as failures
- `TotalTime.P50`: median end-to-end response time
- `TotalTime.P90` or `TotalTime.P95`: slower user experience near the upper end
- `TTFB`: time until the first response byte arrives
- `TCPHandshake` and `TLSHandshake`: connection setup cost
- `WaitingTime`: server processing time after connection overhead

Use **windowed metrics** to find short spikes and changes during a run. Use **cumulative metrics** to understand the overall result.

An average alone is not enough. A healthy average can hide a poor P95 or a short period of severe failures.

---

## 25. What is the difference between windowed and cumulative metrics?

Both views report the same kinds of performance measurements, but they calculate them over different periods.

| View | Data included | Best used for |
|---|---|---|
| **Windowed** | Only requests completed during the latest refresh window | Monitoring the running test and locating sudden changes |
| **Cumulative** | All requests completed since the test started | Evaluating the overall result, reporting, and checking service-level targets |

### Windowed metrics

LPS divides the test into short time windows. The default dashboard refresh interval is five seconds. At the end of each window, LPS calculates metrics using only requests from that window, sends the snapshot to the dashboard, and starts a fresh window.

Use the windowed view to answer questions such as:

- When did latency begin to increase?
- Did errors appear when a new stage started?
- Was there a short performance spike that the overall result may hide?
- Did the system recover after the load decreased?

For example, if 50 requests become very slow during one five-second window, that window's P90 may rise sharply and make the problem visible.

### Cumulative metrics

Cumulative metrics are calculated from all requests collected since the test started. They do not reset at each dashboard refresh.

Use the cumulative view to answer questions such as:

- What was the overall P95 response time?
- What was the total error rate?
- What throughput did the complete run achieve?
- Did the finished test meet its performance targets?

The same 50 slow requests may have little effect on a cumulative result containing tens of thousands of requests. This is why a short problem can be obvious in the windowed view but difficult to see in the cumulative view.

Neither view replaces the other. Use **windowed metrics to understand when behavior changed** and **cumulative metrics to judge the complete test outcome**. A cumulative percentile is calculated from the complete request population; it is not an average of the windowed percentiles.

## 26. Can I configure the LPS dashboard from the command line?

Yes. Use `lps dashboard` to update the persistent dashboard settings:

```bash
lps dashboard --builtindashboard false --port 8009 --refreshrate 5
```

The short form is:

```bash
lps dashboard -bid false -p 8009 -rr 5
```

- `builtindashboard` enables or disables the built-in dashboard UI. Disabling it does not disable the REST API.
- `port` sets the dashboard port and must be between `1` and `65535`.
- `refreshrate` sets the metrics push interval in seconds and must be greater than `0`.

Each option is optional, and omitted settings keep their current values. For example, `lps dashboard --refreshrate 10` changes only the refresh rate. Run `lps dashboard --help` to see all options.

## 27. How should I choose the number of clients and arrival delay?

Base the values on a business workload, not on the largest number your load generator can produce.

A practical sequence is:

1. Identify the important user journey or API operation.
2. Estimate expected and peak concurrency.
3. Start below the expected level.
4. Use `arrivalDelay` or stages to increase traffic gradually.
5. Monitor the target application and its dependencies.
6. Stop if errors or latency exceed agreed safety limits.
7. Repeat with one controlled change at a time.

A lower `arrivalDelay` introduces clients faster. A higher `numberOfClients` creates more concurrent actors. These settings do not guarantee a fixed requests-per-second rate because response time and the selected iteration mode also affect throughput.

## 28. How do I troubleshoot a plan that does not run?

Check these items in order:

1. Confirm LPS is installed with `lps --version`.
2. Confirm the plan path passed to `lps run` is correct.
3. Check the plan with [YAMLlint](https://www.yamllint.com/), then fix any reported syntax or indentation errors. Use spaces consistently and do not use tabs.
4. Confirm field names use the documented camelCase spelling, such as `numberOfClients`, `arrivalDelay`, and `httpRequest`.
5. Confirm every round and iteration has a unique, meaningful name.
6. Confirm the selected mode has its required settings.
7. Check that variables resolve and captured values exist before they are used.
8. Start with one client and one request to separate configuration errors from load-related failures.
9. Confirm the target URL, DNS, certificate, authentication, firewall, and proxy behavior outside LPS.

Do not solve a failing test by immediately increasing load-generator resources. First determine whether the failure is in the plan, the network, the load generator, or the target system.

## 29. Why is my test generating more traffic than expected?

The most common cause is forgetting that iteration settings apply per client.

Check:

- `numberOfClients`
- The number of iterations in the round
- `requestCount` on every `R` or `CRB` iteration
- Per-client `duration` on every `D` or `DCB` iteration
- `batchSize` in burst modes
- Retry policies
- Whether iterations use `runInParallel: true`
- Whether multiple stages overlap

Before running, describe the planned traffic in plain language. For example: "Twenty clients arrive every 500 milliseconds, and each sends 50 requests." If that sentence is not clear, simplify the plan first.

## 30. When should I use distributed testing?

Use distributed testing when one load-generator machine cannot safely produce the required traffic, or when you need traffic from multiple machines.

LPS uses a master/worker model:

- The master prepares the plan, hosts the dashboard, maintains global state, and aggregates worker metrics.
- Workers execute the plan and send their metrics to the master.
- The master does not start workers automatically.

Typical commands are:

```bash
# Configure cluster settings
lps cluster -mip 192.168.1.100 -gp 8999 -ew 2 -miw

# Start the master
lps master plan.yaml

# Run separately on each worker
lps run plan.yaml
```

Verify network access to the configured gRPC port before starting. Begin with a local or small distributed run before attempting high volume.

## 31. How can LPS fit into CI/CD?

Store the YAML plan with the application, run it from the pipeline with `lps run`, and use failure rules to express the performance conditions the release must meet.

A good CI/CD progression is:

1. Run a small smoke plan on every relevant change.
2. Run a stable baseline plan in a controlled test environment.
3. Compare results using the same workload and environment.
4. Integrate LPS with InfluxDB to retain metrics, compare runs over time, and visualize trends in Grafana.
5. Use failure rules for agreed service-level targets.
6. Reserve larger load, stress, and endurance tests for suitable scheduled stages.

For example, this Azure DevOps pipeline installs the .NET 8 SDK and LPS on a clean Ubuntu agent before running a committed plan:

```yaml
trigger:
- main

pool:
  vmImage: ubuntu-latest

steps:
- checkout: self

- task: UseDotNet@2
  displayName: Install .NET 8 SDK
  inputs:
    packageType: sdk
    version: 8.x

- bash: |
    dotnet tool install --global lps
    echo "##vso[task.prependpath]$HOME/.dotnet/tools"
  displayName: Install LPS

- bash: lps run tests/perf/plan.yaml
  displayName: Run LPS performance test
```

This example assumes the plan is committed at `tests/perf/plan.yaml`. Hosted agents are recreated between jobs, so install LPS in the job or provide a prepared self-hosted agent.

Keep the plan deterministic. Avoid mixing major application, environment, data, and workload changes in the same comparison.

Failure rules classify the test result, but the current documentation does not define a guaranteed process exit-code contract for every CI platform. Verify the behavior of the installed LPS version before treating task success or failure as a deployment gate.

## 32. What is a good first real-world test plan?

Start with a baseline that represents one important operation and includes conservative safety limits.

```yaml
name: SearchBaseline
rounds:
- name: BaselineRound
  numberOfClients: 10
  arrivalDelay: 500
  iterations:
  - name: SearchProducts
    mode: D
    duration: 60
    httpRequest:
      url: https://api.example.com/products?q=test
      httpMethod: GET
    failureRules:
    - metric: "TotalTime.P95 > 500"
    - metric: "ErrorRate > 0.01"
      errorStatusCodes: ">= 500"
    terminationRules:
    - metric: "ErrorRate > 0.05"
      gracePeriod: "00:00:10"
      errorStatusCodes: ">= 500"
```

Before running it, replace the URL and thresholds with values appropriate for your system. This example is a structure to adapt, not a universal performance target.

## 33. What performance checks should I run before releasing to production?

Select tests according to what changed and how it could fail. Do not run every test shape for every release.

| Risk area | Useful test shapes | Watch for |
|---|---|---|
| CPU and memory | Gradual load, sustained load, payload scaling, soak | CPU saturation, allocation growth, garbage-collection pauses, memory exhaustion, and rising latency |
| Database, connections, and workers | Concurrent load, peak load, data-volume scaling, dependency latency | Database CPU and I/O, locks, exhausted connection pools, blocked workers, timeouts, and errors |
| Network, payloads, and storage | Payload scaling, large-file workload, mixed CPU and I/O | Serialization cost, network throughput, response size, disk I/O, and processing time |
| Caches | Cold-cache load, cache-expiry burst, hot-key load | Cache misses, database load, uneven shard pressure, and latency spikes |
| Queues and dependencies | Queue overload, burst load, dependency latency or failure injection | Backlog growth, retry storms, pool exhaustion, stalled work, and user-visible errors |
| Scalability and resilience | Gradual, peak, spike, burst, soak, and data-volume scaling | Throughput limits, percentile latency, error rate, recovery time, and nonlinear resource growth |

For each selected test:

1. Reproduce a realistic workload and data volume in an authorized pre-production environment.
2. Define the expected throughput, latency, error-rate, and resource limits before running it.
3. Monitor both LPS metrics and the target system's CPU, memory, database, cache, queue, network, and dependency metrics.
4. Use termination rules for safety and failure rules for release criteria.
5. Store results in InfluxDB and compare them with a stable baseline under the same conditions.

The goal is to determine whether the release makes the system slower, less scalable, less resilient, or more resource-intensive under realistic traffic.
