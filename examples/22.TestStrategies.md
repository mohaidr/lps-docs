# Test Strategy Examples

Use these plans as structural templates, then replace the example URL, workload, client counts, durations, and thresholds with values appropriate for the system under test. Client counts and thresholds below are examples, not universal recommendations.

Before choosing a plan, establish:

- the endpoint and HTTP workload
- expected production traffic
- test duration
- acceptable error-rate and latency thresholds
- whether the goal is validation, degradation detection, or finding a breaking point

Run load tests only against an environment approved for testing.

## Execution Facts That Affect Every Plan

- `numberOfClients` is the number of new clients created by a round or stage.
- `arrivalDelay` is the delay in milliseconds between consecutive client starts. A shorter delay creates a steeper ramp; it does not make each client send requests faster.
- A duration-based iteration starts its `duration` clock separately for each client. If two clients start 500 ms apart, they normally finish about 500 ms apart.
- Rounds run sequentially. The next round starts after the current round completes.
- Stages control client arrival within one round. Stage 2 starts spawning only after every Stage 1 client has been spawned, but it does not wait for Stage 1 clients to finish.
- Stage client counts are additive, not target concurrency values. Stages of 10, 50, and 100 create 160 clients in total.
- Active concurrency at any moment depends on which clients have started and which clients have completed their iterations.
- `batchSize` applies to each client. With 10 clients and `batchSize: 50`, a `CB` iteration can issue up to 500 requests in a wave.
- `terminationRules` terminate an iteration after a condition remains violated for its grace period. `failureRules` classify an iteration after it finishes.

## Load Test

A load test validates expected traffic for a fixed period.

**Example assumptions:** expected traffic is 100 clients, clients should arrive 200 ms apart, and each client should send sequential requests for 30 minutes.

```yaml
name: ExpectedLoadTest
rounds:
- name: ExpectedLoadRound
  numberOfClients: 100
  arrivalDelay: 200
  iterations:
  - name: GetResource
    mode: D
    duration: 1800
    httpRequest:
      url: https://api.example.com/resource
      httpMethod: GET
    failureRules:
    - metric: "ErrorRate > 0.01"
      errorStatusCodes: ">= 500"
    - metric: "TotalTime.P95 > 500"
```

**Traffic pattern:** clients start one at a time over approximately 19.8 seconds. Each client runs for 1,800 seconds from its own start time, so they also finish approximately 200 ms apart. The test reaches approximately 100 active clients before the first client finishes.

**What this plan does not decide:** whether 100 clients, 1% errors, or 500 ms P95 are appropriate for a real service. Those values must come from expected traffic and service objectives.

## Progressive Stress Test

A progressive stress test applies increasingly larger, controlled load levels to identify where service objectives begin to fail.

**Example assumptions:** the approved levels are 50, 100, and 200 clients, and each client runs for five minutes. Separate rounds are used because rounds are sequential; the client counts are therefore separate levels, not a cumulative total of 350 active clients.

```yaml
name: ProgressiveStressTest
variables:
- name: targetUrl
  value: https://api.example.com/resource
iterations:
- name: StressResource
  mode: D
  duration: 300
  httpRequest:
    url: $targetUrl
    httpMethod: GET
  terminationRules:
  - metric: "ErrorRate > 0.10"
    errorStatusCodes: ">= 500"
    gracePeriod: "00:00:30"
  - metric: "TotalTime.P95 > 3000"
    gracePeriod: "00:00:30"
rounds:
- name: Stress50Clients
  numberOfClients: 50
  arrivalDelay: 200
  reference: ["StressResource"]
- name: Stress100Clients
  numberOfClients: 100
  arrivalDelay: 100
  reference: ["StressResource"]
- name: Stress200Clients
  numberOfClients: 200
  arrivalDelay: 50
  reference: ["StressResource"]
```

**Reuse:** `StressResource` is a global iteration referenced by every round, so the request, duration, and rules have one definition. `targetUrl` is a top-level variable so the endpoint can be changed once. Client counts and arrival delays remain on their rounds because they define the visible stress progression.

**Traffic pattern:** the 50-client round completes before the 100-client round starts, and the 100-client round completes before the 200-client round starts. Within each round, every referenced `StressResource` client has its own five-minute duration measured from its individual start time. Shorter arrival delays make each higher level ramp faster.

**Important limitation:** documentation defines termination at the iteration level. Do not assume that terminating one round prevents later rounds from starting unless that behavior has been verified for the installed LPS version. When escalation must stop after the first breached level, place each load level in a separate plan and run the next plan only after reviewing the previous result.

## Soak Test

A soak test holds expected load for several hours to detect gradual latency degradation, resource exhaustion, or memory leaks.

**Example assumptions:** expected sustained traffic is 50 clients, each client runs for eight hours, severe degradation should terminate the iteration, and tighter service objectives should classify its final result.

```yaml
name: EightHourSoakTest
rounds:
- name: SoakRound
  numberOfClients: 50
  arrivalDelay: 200
  iterations:
  - name: SoakResource
    mode: D
    duration: 28800
    httpRequest:
      url: https://api.example.com/resource
      httpMethod: GET
    terminationRules:
    - metric: "ErrorRate > 0.10"
      errorStatusCodes: ">= 500"
      gracePeriod: "00:10:00"
    - metric: "TotalTime.P95 > 5000"
      gracePeriod: "00:10:00"
    failureRules:
    - metric: "ErrorRate > 0.01"
      errorStatusCodes: ">= 500"
    - metric: "TotalTime.P95 > 1000"
```

**Traffic pattern:** clients ramp up over approximately 9.8 seconds. Each client then sends sequential requests for eight hours from its own start time. Clients naturally finish in the same staggered order.

**What this plan does not provide:** server-side memory, CPU, database, or connection-pool measurements. Collect those separately while LPS measures request behavior.

## Spike Test

A spike test introduces a rapid burst of new clients to observe service behavior during the surge and natural recovery.

**Example assumptions:** five baseline clients arrive slowly, 100 spike clients then arrive quickly, and five trailing clients arrive slowly. Every client runs for two minutes from its own start time.

```yaml
name: SuddenSpikeTest
rounds:
- name: SpikeRound
  stages:
  - numberOfClients: 5
    arrivalDelay: 1000
  - numberOfClients: 100
    arrivalDelay: 50
  - numberOfClients: 5
    arrivalDelay: 1000
  iterations:
  - name: SpikeResource
    mode: D
    duration: 120
    httpRequest:
      url: https://api.example.com/resource
      httpMethod: GET
    terminationRules:
    - metric: "ErrorRate > 0.20"
      errorStatusCodes: ">= 500"
      gracePeriod: "00:00:15"
    - metric: "TotalTime.P95 > 5000"
      gracePeriod: "00:00:15"
```

**Traffic pattern:** Stage 1 spawns five clients one second apart. After all five have spawned, Stage 2 starts spawning 100 additional clients 50 ms apart. Stage 3 starts only after all spike clients have spawned and adds five more clients one second apart. Up to 110 clients can overlap because stage counts are additive.

**Natural ramp-down:** the stages do not command concurrency to return to five. Each client finishes two minutes after its own start, so baseline clients finish first, spike clients finish in their faster arrival pattern, and trailing clients finish last. The final stage represents trailing traffic, not a target of five active clients.

**Important limitation:** all stages share the same iteration and duration. Use sequential rounds instead when the requirement is three isolated phases with independently configured baseline, spike, and post-spike durations.

## Continuous Wave Stress Test

`CB` mode sends a batch from each client, waits for the cooldown, and repeats until manually stopped or terminated.

**Example assumptions:** ten clients are approved, each client may send 50 requests per wave, and each client waits one second between waves.

```yaml
name: ContinuousWaveStressTest
rounds:
- name: ContinuousWaveRound
  numberOfClients: 10
  arrivalDelay: 500
  iterations:
  - name: WaveResource
    mode: CB
    batchSize: 50
    coolDownTime: 1000
    httpRequest:
      url: https://api.example.com/resource
      httpMethod: GET
    terminationRules:
    - metric: "ErrorRate > 0.10"
      errorStatusCodes: ">= 500"
      gracePeriod: "00:00:30"
    - metric: "TotalTime.P95 > 3000"
      gracePeriod: "00:00:30"
```

**Traffic pattern:** the ten clients start 500 ms apart. Each client repeatedly sends a batch of 50 requests and then waits one second. Across all clients, a wave can contain up to 500 requests, although actual timing and throughput depend on request completion and scheduling.

**Important limitation:** this is fixed continuous pressure, not an automatic breakpoint search. To find a breakpoint, increase clients or batch size between controlled runs and stop increasing when the approved service objectives are breached. `CB` has no duration limit, so always use termination rules and supervise the test.

## Choosing a Strategy

| Goal | Recommended structure |
| --- | --- |
| Validate expected traffic | One round using `D` mode and failure rules |
| Find degradation across approved load levels | Sequential `D` rounds, or separate plans when escalation must stop after a breach |
| Detect degradation over time | One long-running round using `D` mode |
| Test a sudden traffic surge and natural recovery | Additive stages with rapidly arriving clients using `D` mode |
| Test isolated baseline, spike, and recovery phases | Sequential rounds with independently configured durations |
| Apply fixed continuous request waves | Supervised `CB` mode with termination rules |

When requirements are missing, do not present example values as recommended production settings. Ask for the missing workload details or label every chosen value as an assumption.
