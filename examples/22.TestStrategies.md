# Test Strategy Examples

Use these plans as structural templates, then replace the example URL, workload, client counts, durations, and thresholds with values appropriate for the system under test. Client counts and thresholds below are examples, not universal recommendations.

Before choosing a plan, establish:

- the endpoint and HTTP workload
- expected production traffic
- test duration
- acceptable error-rate and latency thresholds
- whether the goal is validation, degradation detection, or finding a breaking point

Run load tests only against an environment approved for testing.

## Execution Facts That Affect Every Plan

- `numberOfClients` is the number of new clients created by a round or stage.
- `arrivalDelay` is the delay in milliseconds between consecutive client starts. A shorter delay creates a steeper ramp; it does not make each client send requests faster.
- A duration-based iteration starts its `duration` clock separately for each client. If two clients start 500 ms apart, they normally finish about 500 ms apart.
- Rounds run sequentially. The next round starts after the current round completes.
- Stages control client arrival within one round. Stage 2 starts spawning only after every Stage 1 client has been spawned, but it does not wait for Stage 1 clients to finish.
- Stage client counts are additive, not target concurrency values. Stages of 10, 50, and 100 create 160 clients in total.
- Active concurrency at any moment depends on which clients have started and which clients have completed their iterations.
- `batchSize` applies to each client. With 10 clients and `batchSize: 50`, a `CB` iteration can issue up to 500 requests in a wave.
- `terminationRules` terminate an iteration after a condition remains violated for its grace period. `failureRules` classify an iteration after it finishes.

## Dedicated Load-Testing Guides

Each of the six standard load-testing types has a dedicated guide with detailed concepts and runnable LPS configurations:

1. **[Smoke Testing](../articles/21.SmokeTesting.md)** — minimal concurrency (`1–5` clients) to validate scripts, auth, and clean baseline latency.
2. **[Load Testing](../articles/22.LoadTesting.md)** — expected daily and normal peak traffic (`ramp → plateau → drain`).
3. **[Stress Testing](../articles/23.StressTesting.md)** — above-normal rush-hour load (single high plateau or step-up staircase + recovery).
4. **[Spike Testing](../articles/24.SpikeTesting.md)** — sudden flash-crowd burst (`Baseline → Surge → Recovery`).
5. **[Breakpoint Testing](../articles/25.BreakpointTesting.md)** — continuous linear ramp toward a high client ceiling until `terminationRules` (or your planned `duration`) discover your upper capacity limit.
6. **[Soak Testing](../articles/26.SoakTesting.md)** — multi-hour paced endurance (`mode: DCB`) to catch memory and connection leaks.

## Smoke Test

A smoke test verifies that your script, authentication, and target endpoint work cleanly under minimal concurrency (`1–5` clients) before running larger tests. See **[Smoke Testing](../articles/21.SmokeTesting.md)**.

```yaml
name: ApiSmokeTest
variables:
- name: targetUrl
  value: https://api.example.com/resource
rounds:
- name: SmokeRound
  numberOfClients: 3
  arrivalDelay: 500
  iterations:
  - name: VerifyEndpoint
    mode: R
    requestCount: 10
    httpRequest:
      url: $targetUrl
      httpMethod: GET
    failureRules:
    - metric: "ErrorRate > 0"
      errorStatusCodes: ">= 400"
    - metric: "TotalTime.P95 > 500"
```

## Load Test

A load test validates expected production traffic for a sustained period after a controlled warm-up ramp. See **[Load Testing](../articles/22.LoadTesting.md)**.

**Example assumptions:** expected peak traffic is 100 clients, clients ramp smoothly over roughly one minute (`arrivalDelay: 600` ms) to avoid cold-cache or connection-pool shock, and each client runs for 30 minutes (`1800` seconds). Tight `failureRules` grade final SLA compliance while looser safety `terminationRules` stop the run early if the target environment is severely broken.

```yaml
name: ExpectedLoadTest
variables:
- name: targetUrl
  value: https://api.example.com/resource
rounds:
- name: ExpectedLoadRound
  numberOfClients: 100
  arrivalDelay: 600
  iterations:
  - name: GetResource
    mode: D
    duration: 1800
    httpRequest:
      url: $targetUrl
      httpMethod: GET
    failureRules:
    - metric: "ErrorRate > 0.01"
      errorStatusCodes: ">= 500"
    - metric: "TotalTime.P95 > 500"
    terminationRules:
    - metric: "ErrorRate > 0.15"
      errorStatusCodes: ">= 500"
      gracePeriod: "00:01:00"
    - metric: "TotalTime.P95 > 3000"
      gracePeriod: "00:01:00"
```

**Traffic pattern:** clients start one at a time over ~59.4 seconds so caches, JIT, and connection pools warm up gradually. Each client runs for 1,800 seconds from its own start time, holding 100 active clients for ~29 minutes before draining in the same staggered order.

**Choosing `D` versus `DCB`:** `mode: D` sends back-to-back requests with zero pause per client (ideal for maximum-throughput API benchmarks). When modeling human users or paced callers with think time between requests, switch to `mode: DCB` (`batchSize` + `coolDownTime`).

**What this plan does not decide:** whether 100 clients, 1% errors, or 500 ms P95 are appropriate for a real service. Those values must come from expected traffic and service objectives.

## Stress Test

A stress test evaluates stability, degradation, and recovery when traffic rises **above normal operational load** (for example `1.5x–2x` expected peak during rush hours or promotions). Unlike a **[Breakpoint Test](#breakpoint-test-capacity-testing)**, which climbs endlessly until failure, a stress test targets planned overload levels—either as a **single above-peak plateau** (`ramp → high plateau → drain`) or as a **step-up staircase** (`50 → 100 → 200 → step-down`). See **[Stress Testing](../articles/23.StressTesting.md)** for both templates.

### Single Above-Peak Plateau (Simple Default)

```yaml
name: AbovePeakStressTest
variables:
- name: targetUrl
  value: https://api.example.com/resource
rounds:
- name: HighLoadStressRound
  numberOfClients: 200
  arrivalDelay: 600
  iterations:
  - name: StressResource
    mode: D
    duration: 1800
    httpRequest:
      url: $targetUrl
      httpMethod: GET
    failureRules:
    - metric: "ErrorRate > 0.05"
      errorStatusCodes: ">= 500"
    - metric: "TotalTime.P95 > 2000"
    terminationRules:
    - metric: "ErrorRate > 0.20"
      errorStatusCodes: ">= 500"
      gracePeriod: "00:00:30"
    - metric: "TotalTime.P95 > 5000"
      gracePeriod: "00:00:30"
```

### Step-Up Staircase with Recovery Check

**Why a single round with stages:** placing additive `stages` with `startupDelay` plateaus inside **one** round steps active concurrency upward continuously (`50 → 100 → 200`) without dropping traffic to zero between levels, and a `terminationRules` breach at an earlier step stops the test immediately instead of launching higher-load rounds.

**Example assumptions:** expected peak is 50 clients, stress steps escalate from 50 to 100 to 200 active clients in three-minute plateaus, and each client runs for nine minutes (`540` seconds) from its own start time so all three waves overlap at peak and then step down naturally to verify recovery.

```yaml
name: StepUpStressTest
variables:
- name: targetUrl
  value: https://api.example.com/resource
rounds:
- name: StaircaseStressRound
  stages:
  - numberOfClients: 50
    arrivalDelay: 200
  - numberOfClients: 50
    arrivalDelay: 200
    startupDelay: 170000
  - numberOfClients: 100
    arrivalDelay: 100
    startupDelay: 170000
  iterations:
  - name: StressResource
    mode: D
    duration: 540
    httpRequest:
      url: $targetUrl
      httpMethod: GET
    failureRules:
    - metric: "ErrorRate > 0.05"
      errorStatusCodes: ">= 500"
    - metric: "TotalTime.P95 > 2000"
    terminationRules:
    - metric: "ErrorRate > 0.20"
      errorStatusCodes: ">= 500"
      gracePeriod: "00:00:30"
    - metric: "TotalTime.P95 > 5000"
      gracePeriod: "00:00:30"
```

**Traffic and recovery pattern:**
- **Step 1 (`0:00–3:00`):** Stage 1 spawns 50 clients over ~9.8 seconds, then `startupDelay: 170000` holds a steady **50-client** plateau until the 3-minute mark.
- **Step 2 (`3:00–6:00`):** Stage 2 adds 50 clients over ~9.8 seconds while Stage 1 clients are still running, holding **100 active clients** until the 6-minute mark.
- **Step 3 (`6:00–9:00`):** Stage 3 adds 100 clients over ~9.9 seconds, reaching the peak of **200 active clients** (`50 + 50 + 100`) until Stage 1 clients reach their 540-second duration at `9:00`.
- **Step-down recovery (`9:00–15:00`):** Stage 1 clients finish around `9:00` (concurrency drops to **150**), Stage 2 clients finish around `12:00` (drops to **100**), and Stage 3 clients finish around `15:00`—letting you verify whether latency and errors recover once peak overload subsides.

**Observing the breaking point:** cumulative round metrics cover the full staircase, so watch windowed latency and error rates in the live dashboard or Grafana to pinpoint the exact concurrency step where objectives degrade.

**When to use separate rounds instead:** use sequential `rounds` (or separate YAML plans) only when you deliberately want traffic to drain to zero between isolated benchmark levels with independent per-round summary aggregates. Remember that terminating one iteration may not prevent later rounds in the same plan from starting.

## Breakpoint Test (Capacity Testing)

A breakpoint test (also called a *capacity* or *limit* test) discovers your system's upper capacity ceiling when you do not know where it breaks ahead of time (`80`, `350`, or `850` clients). One single round ramps gradually toward a high client ceiling—with **no intermediate plateaus**—until `terminationRules` (or the planned `duration` ceiling) stop the run. See **[Breakpoint Testing](../articles/25.BreakpointTesting.md)**.

**Why `mode: D` with `duration` longer than the ramp is the cleanest default:**
- **Natural sequential speed:** Each client sends the next request as soon as the previous response finishes—no artificial `coolDownTime` assumptions needed.
- **No early client exit AND safe finish:** Setting `duration: 2100` seconds (35 minutes—5 minutes longer than the 30-minute ramp) keeps Client #1 active throughout the entire climb **and** lets the test finish cleanly (`1h 05m` max) if the server survives all 3,000 clients. (Switch to `DCB` if you want think time between requests, or `CB` only for supervised runs with no time limit.)

**Example assumptions:** up to 3,000 clients are authorized, one new client joins every 600 ms (100 new clients per minute over 30 minutes), each client runs sequential requests for up to 35 minutes (`mode: D`, `duration: 2100`), and `terminationRules` halt the climb once 5xx errors or P95 latency stay breached for 15 seconds.

```yaml
name: ContinuousRampBreakpointTest
variables:
- name: targetUrl
  value: https://api.example.com/resource
rounds:
- name: LinearRampToBreakpoint
  numberOfClients: 3000
  arrivalDelay: 600
  iterations:
  - name: BreakpointResource
    mode: D
    duration: 2100
    httpRequest:
      url: $targetUrl
      httpMethod: GET
    failureRules:
    - metric: "ErrorRate > 0.05"
      errorStatusCodes: ">= 500"
    - metric: "TotalTime.P95 > 1500"
    terminationRules:
    - metric: "ErrorRate > 0.15"
      errorStatusCodes: ">= 500"
      gracePeriod: "00:00:15"
    - metric: "TotalTime.P95 > 3000"
      gracePeriod: "00:00:15"
```

**Traffic pattern and reading the breakpoint:**
- Active concurrency climbs diagonally by 100 clients per minute (`0 → 3,000` over 30 minutes) while request throughput scales continuously.
- Because new clients keep arriving during the 15-second `gracePeriod` (~25 clients at `arrivalDelay: 600`), inspect the live dashboard or Grafana windowed charts ~15 seconds before termination to see the exact concurrency where degradation began.
- If the service survives all 3,000 clients without breaching `terminationRules`, Client #1 finishes at `35:00` and Client #3000 finishes at `1:05:00`, evaluating `failureRules`—indicating your breaking point sits above 3,000 clients.

## Soak Test

A soak test holds realistic, paced traffic for several hours to uncover gradual latency creep, memory leaks, connection-pool leaks, or storage exhaustion.

**Why `DCB` pacing matters for soak runs:** running `mode: D` with zero pause for eight hours fires tens of millions of back-to-back requests—turning an endurance check into an unthrottled stress hammer. Using `mode: DCB` (`batchSize` + `coolDownTime`) paces each client steadily over hours.

**Example assumptions:** sustained traffic is 50 clients ramping over ~30 seconds (`arrivalDelay: 600` ms), each client sends one request followed by a one-second pause (`batchSize: 1`, `coolDownTime: 1000`) for eight hours (`28800` seconds), severe degradation terminates the iteration, and tighter service objectives classify the final result.

```yaml
name: EightHourSoakTest
variables:
- name: targetUrl
  value: https://api.example.com/resource
rounds:
- name: SoakRound
  numberOfClients: 50
  arrivalDelay: 600
  iterations:
  - name: SoakResource
    mode: DCB
    duration: 28800
    batchSize: 1
    coolDownTime: 1000
    httpRequest:
      url: $targetUrl
      httpMethod: GET
    failureRules:
    - metric: "ErrorRate > 0.01"
      errorStatusCodes: ">= 500"
    - metric: "TotalTime.P95 > 1000"
    terminationRules:
    - metric: "ErrorRate > 0.10"
      errorStatusCodes: ">= 500"
      gracePeriod: "00:05:00"
    - metric: "TotalTime.P95 > 5000"
      gracePeriod: "00:05:00"
```

**Traffic pattern:** 50 clients ramp up over ~29.4 seconds, then each client sends paced requests (~1 second between requests plus response time) for eight hours from its own start time before draining naturally.

**Important soak-test considerations:**
- **Cumulative `ErrorRate` dilution:** `ErrorRate` is cumulative across the iteration. After seven healthy hours, even a total outage in Hour 8 takes many minutes to push cumulative `ErrorRate` above `0.10`—always monitor windowed error rates and latency trends in the live dashboard or Grafana.
- **Load-generator and socket hygiene:** configure `lps watchdog` so the generator host cannot exhaust local memory or sockets, and set `lps httpclient --poolconnectionlifetime` so pooled connections periodically refresh DNS and load-balancer backends over multi-hour runs.
- **Server-side telemetry:** collect backend memory, GC, CPU, database, and file-descriptor metrics alongside LPS request telemetry.

## Spike Test

A spike test establishes a steady baseline, injects a sudden vertical surge of new clients with no intermediate warm-up steps, and drops back to baseline to verify shock absorption and immediate recovery.

**Why stage `startupDelay` timing matters:** without `startupDelay`, all stages spawn within seconds of each other—leaving almost no baseline or post-spike recovery window. Timing Stage 2 after a steady baseline plateau and spawning Stage 3's recovery clients right before the spike wave finishes (`duration: 60`) produces a true **Baseline → Surge → Recovery** profile without dropping concurrency to zero.

**Example assumptions:** normal baseline is 20 clients, a sudden surge adds 150 clients in ~3 seconds (`arrivalDelay: 20` ms), and every client runs for 60 seconds from its own start time.

```yaml
name: SuddenSpikeTest
variables:
- name: targetUrl
  value: https://api.example.com/resource
rounds:
- name: SpikeAndRecoveryRound
  stages:
  - numberOfClients: 20
    arrivalDelay: 250
  - numberOfClients: 150
    arrivalDelay: 20
    startupDelay: 50000
  - numberOfClients: 20
    arrivalDelay: 250
    startupDelay: 52000
  iterations:
  - name: SpikeResource
    mode: D
    duration: 60
    httpRequest:
      url: $targetUrl
      httpMethod: GET
    failureRules:
    - metric: "ErrorRate > 0.05"
      errorStatusCodes: ">= 500"
    - metric: "TotalTime.P95 > 2000"
    terminationRules:
    - metric: "ErrorRate > 0.25"
      errorStatusCodes: ">= 500"
      gracePeriod: "00:00:15"
    - metric: "TotalTime.P95 > 5000"
      gracePeriod: "00:00:15"
```

**Traffic and recovery pattern (`~2m 55s` total):**
- **Baseline (`0:05–0:55`):** Stage 1 spawns 20 clients over ~4.8 seconds, then `startupDelay: 50000` holds a clean **20-client** baseline for 50 seconds.
- **Vertical surge (`0:55–1:55`):** Stage 2 injects 150 additional clients in ~3 seconds (`arrivalDelay: 20` ms). Active concurrency jumps sharply to **170** (`20 + 150`) before Stage 1 finishes around `1:00–1:05`, holding **150 active spike clients** through `1:55`.
- **Drop to recovery baseline (`1:55–2:50`):** Stage 3 starts around `1:50` (`startupDelay: 52000`) so 20 fresh recovery clients warm up right as the 150 spike clients complete their 60-second duration between `1:55` and `1:58`—leaving a steady **20-client** post-spike plateau for ~52 seconds to confirm latency and errors snap back to baseline.

**Natural completion, not a target command:** stages are additive and never command existing clients to stop early; the sharp drop back to 20 active clients comes from the 150 spike clients naturally completing their 60-second duration while Stage 3's 20 clients continue running. Use sequential rounds instead only when baseline, spike, and recovery require different request definitions or independent round durations with a full drain between phases.

## Sustained Burst / Wave Test (CB Mode)

`CB` mode sends a fixed-size batch of requests from each client, pauses for `coolDownTime`, and repeats open-ended waves until manually stopped or halted by `terminationRules`. Use this pattern for scheduled batch callers, webhook bursts, or queue-draining waves rather than escalating breakpoint stress.

**Example assumptions:** ten clients are approved, each client sends 50 requests per wave, and each client waits one second between waves.

```yaml
name: SustainedBurstWaveTest
variables:
- name: targetUrl
  value: https://api.example.com/resource
rounds:
- name: BurstWaveRound
  numberOfClients: 10
  arrivalDelay: 500
  iterations:
  - name: WaveResource
    mode: CB
    batchSize: 50
    coolDownTime: 1000
    httpRequest:
      url: $targetUrl
      httpMethod: GET
    terminationRules:
    - metric: "ErrorRate > 0.10"
      errorStatusCodes: ">= 500"
      gracePeriod: "00:00:30"
    - metric: "TotalTime.P95 > 3000"
      gracePeriod: "00:00:30"
```

**Traffic pattern:** the ten clients start 500 ms apart. Each client repeatedly sends a batch of 50 requests and then waits one second. Across all clients, a wave can issue up to 500 requests, although actual timing and overlap depend on response latency.

**Important limitation:** this applies fixed recurring wave pressure at a small constant client count, not an escalating capacity search (use **[Breakpoint Test](#breakpoint-test-capacity-testing)** for discovering upper limits or **[Stress Test](#stress-test)** for above-peak overload). Because `CB` has no duration limit, always include `terminationRules` and supervise the run.

## Choosing a Strategy

| Type | Goal | Recommended LPS structure |
| --- | --- | --- |
| **[Smoke](../articles/21.SmokeTesting.md)** | Verify script logic, auth, and baseline latency | `1–5` clients, `mode: R` (small `requestCount`), zero-error `failureRules` |
| **[Load](../articles/22.LoadTesting.md)** | Validate expected normal & peak traffic | One round with smooth `arrivalDelay` warm-up, `D` (or paced `DCB`) mode, `failureRules`, and safety `terminationRules` |
| **[Stress](../articles/23.StressTesting.md)** | Verify stability & recovery above normal load | Single high plateau (`D`/`DCB`) or one round with additive `stages` + `startupDelay` plateaus and `terminationRules` |
| **[Spike](../articles/24.SpikeTesting.md)** | Survive a sudden flash surge & recover to baseline | One round with 3 additive `stages` + `startupDelay` timed for baseline, rapid-arrival surge, and post-spike recovery |
| **[Breakpoint](../articles/25.BreakpointTesting.md)** | Discover unknown maximum capacity ceiling | One round with high `numberOfClients` (`3000`), gradual `arrivalDelay` (`600` ms = 30m ramp), `mode: D` with `duration: 2100` (35m), `failureRules`, and `terminationRules` |
| **[Soak](../articles/26.SoakTesting.md)** | Detect memory/resource leaks over hours | One multi-hour round using paced `DCB` mode (`batchSize` + `coolDownTime`), `failureRules`, and `terminationRules` |
| **Burst Waves** | Apply recurring fixed-size request waves | Supervised `CB` mode (`batchSize` + `coolDownTime`) with `terminationRules` |

When requirements are missing, do not present example values as recommended production settings. Ask for the missing workload details or label every chosen value as an assumption.
